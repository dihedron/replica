# veho: webhooks for job completion (backlog 11)

- **Status:** approved 2026-11-24; implemented 2026-11-24 except the platform administrator's list and disable (§2, first row), which waits for a cross-tenant administration API (open point 4)
- **Decides:** OI-8 (`veho_specification.md`): polling and long polling stay the primary mechanism; webhooks are an optional addition, **off by default**, that call only endpoints a tenant registered, under the SSRF rules (SEC-12, SEC-13), signed and retried from an outbox.
- **Model:** ligo's `internal/notify` (transactional outbox, singleton dispatcher, HMAC signature, at least once), adapted: ligo's webhooks are configured by the operator, veho's are registered by tenants.

## 1. What it is

A tenant registers HTTPS URLs; when one of its jobs reaches a terminal state, veho posts a small signed JSON document to each URL that subscribed to that event. A webhook is a hint to look: it carries no object data, and a client that misses it finds the same state by polling.

## 2. Decisions

| Question | Decision |
| :-- | :-- |
| Who registers | A tenant `admin` (SEC-21's roles); the platform administrator may list and disable any, never read a secret |
| Where | New table `veho.webhooks` (tenant-scoped, row-level security as the other tenant tables); in `001_core.sql`, edited in place (no migration before the first deployment) |
| Events (v1) | `job.succeeded`, `job.failed`, `job.cancelled`: the job's terminal states. Per-destination events come later |
| When written | The event is inserted into `veho.webhook_outbox` **in the transaction that settles the job** (INV-1): a job never settles without its event, and a delivery never blocks the job |
| Delivery | One dispatcher at a time (advisory lock, as the housekeeping loop); at least once; the event id is the deduplication key; per-webhook backoff, doubling from 30 s to 1 h, 12 attempts, then `abandoned` |
| Signature | `veho-signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, t + "." + body)>`; the receiver rejects a `t` older than 5 minutes |
| Secret | Generated by veho, shown once, kept in the secret store (envelope-encrypted); rotation keeps the old secret valid for 24 h and signs with both (`v1` twice) |
| Off by default | `notifications.enabled: false`; the API refuses to register a webhook while it is off (`FailedPrecondition`) |

## 3. Contract

### 3.1 Resource

```
Webhook { id, name, url (https only), events [job.succeeded|job.failed|job.cancelled],
          enabled, created_at, disabled_reason, last_success_at, last_failure_at }
```

API (protobuf, gRPC and REST like the rest): `CreateWebhook` (returns the secret once), `GetWebhook`, `ListWebhooks`, `UpdateWebhook` (events, enabled), `RotateWebhookSecret`, `DeleteWebhook`, `TestWebhook` (a signed `ping` event, synchronous, result returned, not stored). CLI: `veho webhook create|show|list|update|rotate|delete|test`. Audit actions: `WEBHOOK_CREATE`, `WEBHOOK_UPDATE`, `WEBHOOK_ROTATE`, `WEBHOOK_DELETE`, `WEBHOOK_DISABLE` (automatic), `WEBHOOK_DELIVERY_ABANDONED`.

### 3.2 Payload

```json
{"id": "<event uuid>", "type": "job.succeeded", "occurred_at": "<RFC 3339>",
 "tenant_id": "...", "job": {"id": "...", "state": "SUCCEEDED", "settled_at": "...",
 "destinations": {"succeeded": 2, "failed": 0}}}
```

No source or destination paths, no object names, no error text beyond the job's error class: the receiver reads the details with the API under its own credentials. Body at most 4 KiB.

### 3.3 The request

`POST`, `content-type: application/json`, `veho-event-id`, `veho-event-type`, `veho-signature`, `user-agent: veho/<version>`. A `2xx` within 10 s is a success; anything else (also a redirect: they are not followed) is a failure. The response body is read to at most 1 KiB, for the log, and never stored.

### 3.4 Limits

Per tenant: 10 webhooks, and the outbox of one webhook at most 10,000 pending events (beyond it the oldest `abandoned` first, with an audit entry). A webhook that fails 12 consecutive deliveries (about a day) is disabled with `disabled_reason`, and `WEBHOOK_DISABLE` audited; the tenant re-enables it. Retention: delivered 24 h, abandoned 30 days (`notifications.delivered_retention`, `abandoned_retention`).

## 4. Threat model

| ID | Threat | Mitigation |
| :-- | :-- | :-- |
| W-1 | SSRF: a tenant points a webhook at the metadata service, the lab or an internal service | `https` only; the URL's host is resolved at connect time and **each address checked** after resolution (the dialer's control hook), refusing loopback, link-local, private, unique-local, multicast and the cloud metadata addresses, unless the operator lists a CIDR in `notifications.allow_cidrs` (empty by default); no redirects; no proxy from the environment; DNS rebinding is closed by checking the address actually dialled |
| W-2 | The URL leaks or probes: error text or timing reveal what is behind it | The tenant sees only `success`, `status code` and `timeout`/`connect error`/`tls error` classes; never a response body or a resolved address |
| W-3 | Forged events: a third party posts to the receiver pretending to be veho | HMAC-SHA256 with a per-webhook secret, a timestamp inside the signed string, and the event id for replay detection; the Operator's Guide gives receivers a verification recipe |
| W-4 | The secret is stolen from the database or a backup | Envelope-encrypted in the secret store; shown once; rotation with an overlap; never in logs, audit entries or the outbox |
| W-5 | Amplification: a tenant makes veho post many requests to a victim | At most 10 webhooks per tenant, one request in flight per webhook, backoff, the pending cap of §3.4, a global dispatcher concurrency of 16, and URLs checked by W-1 |
| W-6 | A slow or hostile receiver stalls delivery for everyone | 10 s total timeout, 1 KiB read, no keep-alive reuse across tenants, per-webhook queue (a stuck webhook delays only itself) |
| W-7 | A webhook leaks data across tenants | The payload carries ids and counts of the tenant's own job; the outbox row and the webhook have the tenant's row-level security; the dispatcher reads them as the worker role, scoped by the row's tenant |
| W-8 | The event is lost, or delivered for a job that did not settle | Written in the settling transaction (INV-1); at least once, the id deduplicates; a missed event never costs correctness, polling still shows the state |
| W-9 | A secret or token in the payload or the URL | The URL may not carry userinfo; query strings are allowed but logged without them; the payload holds no secret by construction |
| W-10 | Registration abused to enumerate the internal network by response time | W-1 refuses internal addresses before any connection; `TestWebhook` is rate-limited (6 per minute per tenant) |

## 5. Tests (written first)

| ID | What |
| :-- | :-- |
| WH-T1 | Signature: known vectors, tampered body, old timestamp, rotation with both secrets |
| WH-T2 | SSRF: loopback, private, link-local, metadata, IPv6 forms, a name resolving to a private address, a rebinding resolver that answers public then private, a redirect to an internal URL: all refused, with no connection made to the target |
| WH-T3 | Outbox: the event exists exactly when the job settled (rolled-back settle leaves none); a crash after commit still delivers |
| WH-T4 | Delivery: at-least-once under a receiver that fails then recovers; backoff schedule; abandonment and disabling; ordering is not promised and the docs say so |
| WH-T5 | Tenancy: tenant A cannot read, list, change or receive tenant B's webhooks and events (INV-4); the platform administrator cannot read a secret |
| WH-T6 | Limits: webhook count, pending cap, `TestWebhook` rate, body size |
| WH-T7 | Off by default: with `notifications.enabled: false` no outbox rows are written and the API refuses `CreateWebhook` |
| AC-W1 (lab) | The 8-hour soak's chaos with webhooks on: every settled job produces at least one delivery to a receiver, no job without its event, duplicates carry the same id |

## 6. Documentation

Operator's Guide: enabling, `allow_cidrs`, metrics (`veho_webhook_deliveries_total{result}`, `veho_webhook_outbox_pending`), what to do with an abandoned webhook. Architecture Guide: the outbox and the dispatcher. A *Receiving webhooks* chapter for tenants, with the verification recipe in Go, Python and shell.

## 7. Open points

1. Per-destination events (`transfer.succeeded`) and an event for a destination that failed while the job continues.
2. Whether a tenant may register a webhook to a private network (an operator-listed CIDR is global today; a per-tenant allow list is a later refinement).
3. Mutual TLS to the receiver.
4. The platform administrator listing and disabling any tenant's webhook (§2): needs cross-tenant functions and an `AdminService` call; until then the operator disables one with SQL, and `WEBHOOK_DISABLE` is audited only for automatic disabling.
5. Chaos coverage (AC-W1): the soak with webhooks on, in the lab, as an overnight run (AGENTS.md rule 14).

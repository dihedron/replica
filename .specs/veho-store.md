# veho: the state store

This file specifies chunk C2 (`veho-implementation-plan.md`): the database roles, the schema of the core tables, row-level security, migrations, the connection pools and the start-up checks. It is part of `veho_specification.md` and settles the threat model's open point on "the exact roles and privileges of the database" (`veho-threat-model.md`, T-03, T-17).

Status: approved 2026-11-21 (roles of §2 and the split of §1); implemented in C2.

## 1. Scope

In C2: roles, the schema `veho` with `tenants`, `locations`, `endpoints`, `policies`, `jobs`, `transfers`, `parts` and `executors`, row-level security on the tenant tables, `veho migrate`, the pools, the tenant-scoped transaction, the advisory-lock helper, the start-up checks that concern PostgreSQL (§7).

Not in C2, each in the chunk that uses it (added to `001_core.sql`, §5): `secrets` and `kek` (C3), the audit tables and functions (C4), `internal/jcs` (C4, the first user of canonical JSON). This differs from the implementation plan, which put all tables in C2: a table without the code that reads it cannot be tested against its spec.

## 2. Roles

Created by operations, once, as a superuser, with `packaging/postgres/roles.sql` (as ligo's `test/lab/sql/roles.sql`): roles are cluster objects, and a migration that creates roles would need a superuser at every upgrade. The lab and CI run the same file.

| Role | Owns | Can | Used by |
| :--- | :--- | :--- | :--- |
| `veho_migrator` | the database `veho`, the schema `veho` and every object in it | DDL; nothing at run time | `veho migrate` |
| `veho_dbos` | the schema `dbos` (DBOS creates its tables there at launch) | DBOS's own tables | the DBOS context of every node |
| `veho_api` | nothing | under row-level security: all DML on `endpoints` and `policies`, `SELECT`, `INSERT`, `UPDATE` (no `DELETE`) on `jobs`, `transfers`, `parts`; `SELECT` on `locations` and `executors`; `INSERT`, `SELECT`, `UPDATE` on DBOS's tables (transactional enqueue, EXT-1) | the API handlers |
| `veho_worker` | nothing | all DML on `jobs`, `transfers`, `parts` under row-level security; `SELECT` on `tenants`, `endpoints`, `policies`, `locations`; DML on `executors`; the housekeeping functions (§4.3) | workflow steps, the reconciler, housekeeping |

- None is a superuser or has `BYPASSRLS`; only `veho_migrator` and `veho_dbos` own objects. The owner of the tables, `veho_migrator`, is exempt from row-level security (no `FORCE`): that is what lets the `SECURITY DEFINER` functions of §4.2 and §4.3 work, and the owner is not used at run time otherwise.
- `PUBLIC` loses every privilege on the database and the schemas. `search_path` is set per role (`veho, dbos` for the API, `veho` for the worker and the migrator, `dbos` for DBOS), and the application qualifies every name anyway. `roles.sql` creates the schemas; migration 001 grants `USAGE` on `veho` again, so a schema recreated by the migrator (as the tests do) works.
- DBOS's tables are created by `veho_dbos` after the roles exist; `roles.sql` therefore sets `ALTER DEFAULT PRIVILEGES FOR ROLE veho_dbos IN SCHEMA dbos` for `veho_api` and `veho_worker`, so that the grants follow every table DBOS creates or adds in a later version.
- Why two application roles (SEC-5, T-03): the API acts for an authenticated tenant; the worker acts for the tenant of a transfer. Both are scoped by row-level security; the worker cannot create or change endpoints, policies or tenants, so a bug in a step cannot rewrite configuration, and the API cannot touch `executors`.

## 3. Schema

All application objects are in the schema `veho`. Identifiers are `uuid` (generated by the application, `uuidv7()` is not in PostgreSQL 16); times are `timestamptz` from the database's clock (`now()`, T-27). Every state column has a `CHECK` with the states of `veho-job-lifecycle.md` §2.

```
tenants(id uuid PK, name text UNIQUE, state text CHECK (active|suspended), quotas jsonb, created_at)
locations(id text PK, level text, parent_id text NULL REFERENCES locations, created_at)
endpoints(id uuid PK, tenant_id uuid REFERENCES tenants, name text, location_id text REFERENCES locations,
          driver text, config jsonb, credential_ref text NULL, created_at,
          UNIQUE (tenant_id, id), UNIQUE (tenant_id, name))
policies(id uuid PK, tenant_id uuid, name text, version int, spec jsonb, created_at,
         UNIQUE (tenant_id, id), UNIQUE (tenant_id, name, version))
jobs(id uuid PK, tenant_id uuid, idempotency_key text NULL, source_endpoint_id uuid, source_path text,
     source_info jsonb, policy jsonb, policy_ref uuid NULL, state text, copies_done int,
     satisfied_at, completed_at, settled_at, deadline_at, cancel_requested bool,
     created_at, updated_at, finished_at, last_error jsonb NULL,
     UNIQUE (tenant_id, id), UNIQUE (tenant_id, idempotency_key),
     FOREIGN KEY (tenant_id, source_endpoint_id) REFERENCES endpoints (tenant_id, id),
     FOREIGN KEY (tenant_id, policy_ref) REFERENCES policies (tenant_id, id))
transfers(id uuid PK, tenant_id uuid, job_id uuid, destination_endpoint_id uuid, position jsonb, dest_path text,
          state text, attempt int, adoptions int, bytes_done bigint, bytes_total bigint NULL,
          resume_token jsonb NULL, lease_owner text NULL, lease_expires_at NULL, fence bigint,
          last_error jsonb NULL, started_at NULL, finished_at NULL,
          UNIQUE (tenant_id, id), UNIQUE (job_id, destination_endpoint_id),
          FOREIGN KEY (tenant_id, job_id) REFERENCES jobs (tenant_id, id) ON DELETE CASCADE,
          FOREIGN KEY (tenant_id, destination_endpoint_id) REFERENCES endpoints (tenant_id, id))
parts(tenant_id uuid, transfer_id uuid, part_no int, "offset" bigint, length bigint, sha256 bytea, etag text NULL,
      state text CHECK (committed), PRIMARY KEY (transfer_id, part_no),
      FOREIGN KEY (tenant_id, transfer_id) REFERENCES transfers (tenant_id, id) ON DELETE CASCADE)
executors(id text PK, region text, app_version text, started_at, last_seen)
```

- **Cross-tenant references are impossible** by construction: every reference between tenant tables is a composite foreign key on `(tenant_id, id)` (SEC-6).
- `jobs.policy` and `transfers.position` are immutable snapshots (DP-9): a trigger refuses, with SQLSTATE 23000, an `UPDATE` that changes `jobs.id`, `tenant_id`, `idempotency_key`, `source_endpoint_id`, `source_path`, `policy`, `policy_ref` or `created_at`, or `transfers.id`, `tenant_id`, `job_id`, `destination_endpoint_id`, `position` or `dest_path`. `jobs.source_info` stays mutable: the size and digests are known only after the first read.
- Indexes beyond the keys: `transfers (tenant_id, state)`, `transfers (lease_expires_at) WHERE state IN (COPYING, VERIFYING)`, `jobs (tenant_id, state, created_at)`.
- `ON DELETE CASCADE` only from a job to its transfers and parts, for retention (`veho-audit-housekeeping.md` §3); nothing else cascades.

## 4. Row-level security

### 4.1 The tenant of a transaction

The application sets the tenant per transaction: `SELECT set_config('veho.tenant_id', $1, true)`, the parameterized form of `SET LOCAL`. The function `veho.current_tenant()` returns it as a `uuid`, or `NULL` when unset or empty, so a statement without a tenant sees and changes nothing (fail closed, T-03).

### 4.2 Policies

On every tenant table (`endpoints`, `policies`, `jobs`, `transfers`, `parts`): `ENABLE ROW LEVEL SECURITY` and one policy `USING (tenant_id = veho.current_tenant()) WITH CHECK (tenant_id = veho.current_tenant())` for the application roles. `tenants` is visible to the API and the worker only for the current tenant (`id = veho.current_tenant()`).

Platform operations (creating a tenant, registering a location) are API calls of the `platform-admin` role (SEC-4). They run as `veho_api` through `SECURITY DEFINER` functions owned by `veho_migrator` (`veho.create_tenant`, `veho.put_location`), which check their arguments and cannot be used to read another tenant's rows.

### 4.3 What crosses tenants

Two things must see every tenant: the reconciler (expired leases, `veho-job-lifecycle.md` §6) and retention (settled jobs older than the retention, `veho-audit-housekeeping.md` §3). They do not get `BYPASSRLS`; they call `SECURITY DEFINER` functions owned by `veho_migrator` that return only identifiers and tenants (`veho.expired_transfers(limit)`, `veho.settled_jobs_before(ts, limit)`). The worker then sets the tenant of each row before it acts on it. Retention's delete of a job runs under that tenant like any other statement.

## 5. Migrations

- SQL files embedded in the binary (`migrations/NNN_description.sql`), applied in order by `veho migrate` as `veho_migrator` (DSN from the variable `VEHO_MIGRATOR_DATABASE_URL`, or the one named by `--dsn-env`; never on the command line), each in its own transaction, recorded in `veho.schema_migrations (version, name, sha256, applied_at)`, under an advisory lock so that two nodes cannot migrate at once. An applied file whose checksum changed stops the migration: a change is a new file. (Copied from ligo's `internal/store/migrate`.) **Until a first deployment exists, there is one migration, `001_core.sql`, edited in place** (decision of 2026-11-21): a database created before an edit is recreated (`drop schema veho cascade`, then `veho migrate`; in the lab `test/lab/lab.sh schema-reset`); new migration files start with the first release that is deployed.
- Migrations are expand-only within a release series (`veho-acceptance-matrix.md` §3); `veho serve` refuses to start when the database is ahead of or behind the migrations it carries (`schema_migrations` against its embedded list), naming the difference.

## 6. Connections

- Every pool dials each host with a 5 s timeout (`store.dial`), DBOS's included: with several hosts, a member that does not answer (a partitioned region, listed first) then costs seconds before the next is tried, not the operating system's two minutes (found by AC-6). The timeout is the dialer's, not pgx's `connect_timeout`, and its error does not wrap `context.DeadlineExceeded`: DBOS retries a failed connection only when it does not, and with `connect_timeout` a failover made DBOS give up and end its workflows (found by AC-5). DBOS therefore gets its pool from veho (`store.DBOSPool`, built as DBOS builds its own: 20 connections, an idle-in-transaction timeout of a minute), and a `connect_timeout` in a DSN is overridden.

- Two pools per node, `api` and `worker`, plus DBOS's own (as `veho_dbos`); each DSN is a multi-host DSN with `target_session_attrs=read-write` and `sslmode=verify-full` (refused otherwise, as in ligo; an explicit `allow_insecure` exists for tests only).
- `application_name` is `veho/<executor-id>/<pool>`; statement timeouts per pool (`api` 5 s, `worker` 30 s by default).
- The tenant-scoped transaction is the only way the application touches tenant tables: `store.InTenant(ctx, pool, tenantID, func(tx) error)` begins, sets the tenant, runs the function and commits; any error rolls back.
- The advisory-lock helper `store.TryLock` (copied from ligo) holds a session lock on a connection of its own, for the singletons of housekeeping.

## 7. Start-up checks

At start, on the worker pool (`veho-architecture.md` §7.3, backlog 30); each with a severity from `veho.yaml`'s `checks` block, `refuse` (the default: the node does not start) or `warn` (it logs the failure and starts), for a tier-2 PostgreSQL managed by others (decided 2026-11-22, for review):

| ID | Check | Key | Fails when |
| :--- | :--- | :--- | :--- |
| STO-C1 | Direct connection to a primary | `checks.primary` | `pg_is_in_recovery()` is true, or the session is not on a real backend (`SHOW server_version` answered by a pooler: the backend PID is 0 or `pg_backend_pid()` changes between two calls) |
| STO-C2 | Synchronous commit | `checks.synchronous_commit` | `synchronous_commit` is `off` or `local` |
| STO-C3 | Quorum over other regions | `checks.quorum` | `synchronous_standby_names` is empty or not of the form `ANY n (...)` with `n >= 1` |
| STO-C4 | Schema version | none: always refuses | §5; a node on another schema could corrupt the data |
| STO-C5 | Clock | `checks.clock` | the node's clock differs from the database's by more than `checks.max_clock_offset` [1s], measured as `now()` against the midpoint of the query's round trip. Leases are compared on the database's clock, but logs, audit events, token expiry and certificate validity use the node's |

The unwrap key is checked when the node loads its keyring (`veho-secrets.md`): a node that cannot unwrap the active KEK never starts, whatever the severities.

## 8. Requirements

- **STO-1** `veho migrate` on an empty database creates the schema; a second run applies nothing; a changed applied file stops it with `ErrChanged`.
- **STO-2** Two concurrent `veho migrate` apply each migration once.
- **STO-3** As `veho_api` or `veho_worker`, a statement outside `InTenant` sees no row of any tenant table and inserts none.
- **STO-4** Under tenant T1, no row of T2 is visible, updatable or deletable, and an insert with `tenant_id` T2 is refused; a job of T1 cannot reference an endpoint of T2.
- **STO-5** `veho_worker` cannot insert or update `endpoints`, `policies`, `tenants`; `veho_api` cannot write `executors`; neither can run DDL.
- **STO-6** The immutable columns of `jobs` and `transfers` cannot be updated by any role.
- **STO-7** The cross-tenant functions return identifiers only and work without a tenant set.
- **STO-8** The pools refuse a DSN without `verify-full`.
- **STO-9** The start-up checks pass on the lab, and fail (in tests) on a standby, on `synchronous_commit = local` and on an empty `synchronous_standby_names`.
- **STO-10** A job inserted and a DBOS workflow enqueued in one `veho_api` transaction commit or roll back together (INV-1, EXT-1), with the roles of §2.

Tests: integration tests, tag `integration`, against `VEHO_TEST_DATABASE_URL` (as `veho_migrator`), `VEHO_TEST_API_DATABASE_URL`, `VEHO_TEST_WORKER_DATABASE_URL` and `VEHO_TEST_DBOS_DATABASE_URL`, skipped when unset; the lab sets them (`lab.sh env`). Unit tests for the DSN checks and the migration scan. A fuzz test of the migration file scanner is not worth it (fixed inputs).

# replica: threat model

This file is the threat model (STRIDE) of `replica`, version 0.1.0 of the specification. It closes OI-14: `AGENTS.md` (rule 3) asks for a threat model before the design of a complex solution is implemented, and every mitigation below is a requirement of the specification or of a topic specification, or becomes one when the affected component is specified. It is part of `replica_specification.md`.

Status: draft, 2026-11-21, for review. Written before any implementation, from the design and from the DBOS spike (`replica-dbos-spike.md`); to be reviewed with the answers to OI-1 to OI-10 and OI-12, which can add or remove threats (a Keystone-based authentication, a different completion rule, out-of-process plugins).

## 1. Assets and actors

**Assets.**

1. The objects being replicated: their content (confidentiality, integrity) and the availability of the copies.
2. The tenants' storage credentials (S3 keys and roles, Glance and Keystone credentials).
3. The state store: jobs, transfers, endpoints, quotas, the audit log, and DBOS's own tables, which hold workflow inputs, step outputs and errors.
4. The service's availability, and the fairness between tenants.
5. The release artifacts and the packaging key that signs them.

**Actors.**

- *Tenant users and automation* (operators, viewers, an admin per tenant): trusted to act inside their tenant only.
- *Platform administrators:* manage tenants and global limits; trusted, but not to read tenant data without an audited break-glass action (SEC-4).
- *Other tenants:* hostile until proven otherwise; the main adversary of a multi-tenant design.
- *Network attackers* between regions and between a node and a storage system.
- *Operators of the infrastructure* (hosts, PostgreSQL, etcd, storage): trusted for availability, not for tenant data in the clear where it can be avoided.
- *Compromised or malicious storage endpoints*, and *a compromised plugin or dependency.*

## 2. Trust boundaries

1. **Client to API:** tenant users and automation over HTTPS, authenticated by OIDC bearer tokens or API keys (`replica-api.md` §1).
2. **Node to state store:** `replica serve` to PostgreSQL, across regions, under separate database roles with row-level security (SEC-5).
3. **Inter-region infrastructure:** PostgreSQL streaming replication, etcd and Patroni between the three regions (`replica-architecture.md` §3).
4. **Data plane:** a node to the source and the destination storage systems, with tenant credentials, streaming the object.
5. **Plugins:** drivers compiled into the process (v1); out-of-process drivers are future work (ADR-7).
6. **Secrets:** the node to the secret backends that hold the credentials (SEC-9).
7. **Tenant to tenant:** the isolation of everything a tenant owns from everything another owns, and of both from the platform (SEC-1 to SEC-8).
8. **Host:** configuration and environment files, the service account, the node's memory and logs.
9. **Supply chain:** source, dependencies, build, release artifacts, and their verification by operators.

## 3. Threat matrix

| ID | STRIDE | Boundary | Threat | Mitigations (normative) |
| :--- | :--- | :--- | :--- | :--- |
| T-01 | Spoofing | 1 | A stolen or forged bearer token or API key acts as a tenant. | OIDC validation of issuer, audience, signature and `exp`, with a bounded lifetime and clock skew (SEC-2); the tenant comes from the verified claim only, never from the URL or body; API keys hashed, shown once, revocable (SEC-16); rate limits per principal (SEC-18); every request audited (SEC-17). |
| T-02 | EoP | 1/7 | A tenant reads, cancels or retries another tenant's job by guessing or reusing its ID, or by listing. | Unguessable random IDs (UUID v4); every query scoped by tenant and protected by row-level security (SEC-5); a job of another tenant answers `404`, indistinguishable from a missing one (INV-4, API codes); pagination cursors bound to the tenant; AC-14. |
| T-03 | EoP | 2/7 | The reconciler and the executors, which touch every tenant's rows, are used to bypass row-level security: a bug or an injected ID makes them act on the wrong tenant. | A separate database role for the reconciler and the executors, without superuser or `BYPASSRLS`, whose scope is explicit and audited (SEC-5); every step sets the tenant of its transfer (`SET LOCAL`) before touching tenant data and fails closed if it is unset; composite foreign keys `(tenant_id, id)` (SEC-6); tests that run the executor's queries as a hostile tenant's transfer. |
| T-04 | Spoofing / Info disclosure | 1/4 | **Server-side request forgery.** A submitted source URL makes a node read an internal service, a cloud metadata endpoint or a loopback port, and the content ends up in a destination the attacker reads. | A source URL must resolve to a registered endpoint of the submitting tenant (SEC-12, INV-6); the `http` driver resolves DNS and refuses loopback, link-local, private and metadata ranges unless the endpoint is flagged `allow_private` by a platform administrator, checks again at connection time against DNS rebinding, and follows no redirect to another host (SEC-13); destination paths normalised (SEC-14); AC-14. |
| T-05 | EoP / Info disclosure | 4/7 | **Confused deputy.** A job refers to another tenant's endpoint, or a node uses one tenant's credentials for another tenant's transfer. A role assumed on behalf of a tenant is assumed by another tenant that knows the role's name. | Composite foreign keys forbid cross-tenant endpoint references (SEC-6); credentials are resolved per attempt for the endpoint of that transfer and a driver client is never reused across tenants (SEC-8, PLG-6); role assumption uses a per-tenant external ID (SEC-11). |
| T-06 | Info disclosure | 2/8 | Credentials, tokens or presigned URLs persist in places many people can read: DBOS workflow inputs and step outputs and errors (stored as is in the system database), logs, metrics, API errors, the audit log. | Workflow inputs carry IDs only (SEC-7); step outputs and errors are sanitised before they are returned, because DBOS persists them; credentials are fetched just in time and held in memory for one attempt only (SEC-10); secret types with redacting `String()` and `MarshalJSON`; no URL with a query string in a log; endpoint secrets are never returned by the API (SEC-9); INV-5 is tested by scanning the system database and the logs of the lab for a canary secret. |
| T-07 | Info disclosure / Tampering | 3/4 | Eavesdropping on or altering the object, the credentials or the state in transit between regions and to the storage systems. | TLS 1.2 or later everywhere, mTLS for PostgreSQL and etcd (SEC-15); certificate verification of storage endpoints on by default, off only by an explicit, audited endpoint flag; checksums protect the content end to end (T-08). |
| T-08 | Tampering | 4 | An object is corrupted or altered on the way, or a part is written wrongly, and the copy is reported as done. | The SHA-256 of the object is computed while streaming and compared with the digest recorded at the first read and with the destination's own integrity metadata before `SUCCEEDED` (FR-8); a mismatch is an `Integrity` error: the copy is restarted, and fails after three (`replica-job-lifecycle.md` §7); a pending destination fed from a completed one must match the first digest (FR-10); AC-10. |
| T-09 | Tampering | 4 | **Time of check to time of use.** The source object changes between its `Stat` and the end of the copy, so the destinations hold a mix of two versions. | Every `ReadRange` carries the version recorded at `Stat` and fails with `SourceChanged` when it differs (PLG interface); `SOURCE_CHANGED` is a permanent error unless the policy allows a restart; AC-11. |
| T-10 | Tampering | 4/5 | A reader sees a partly written object under its final name, or an aborted upload leaves one behind. | Writes go to a staging location and `Commit` is atomic and idempotent (FR-9, PLG-7, PLG-8, INV-2); the conformance suite checks that nothing is visible before `Commit` and that `Abort` leaves nothing; AC-16. |
| T-11 | DoS | 1/7 | One tenant exhausts the service: many jobs, huge objects, all the bandwidth, the queue. | Per-tenant quotas: active jobs, bytes in flight, object size, destinations per job, bandwidth (`replica-job-lifecycle.md` §8, SEC quotas); a partitioned queue per tenant, so that a tenant's concurrency limit is its own; token-bucket limiters per node and tenant; submission refused with `429` and `Retry-After`; AC-15. |
| T-12 | DoS | 4 | A slow, stalling or hostile storage endpoint holds workers and connections indefinitely (a tarpit). | Every storage call has a `context.Context` deadline (PLG-6); each part has its own timeout; a transfer has a deadline (`deadline_at`, default 7 days); a bounded number of parts in flight per transfer (NFR-5) and of transfers per endpoint; the lease expires if progress stops (`replica-job-lifecycle.md` §6). |
| T-13 | DoS | 3 | The state store loses its quorum (a region is partitioned, or two regions are down). | By design the service chooses consistency over availability (ADR-3, NFR-2): submission refuses with `503` and a `retryable` flag, reads of the last state may be served stale and flagged; nodes in the minority fence themselves; recovery needs no manual step once the majority is back; AC-5, AC-6; accepted as R-05. |
| T-14 | Tampering | 3 | **Split brain:** two PostgreSQL primaries accept different writes, or a stale standby is promoted and loses committed jobs. | Patroni with a three-member etcd (one per region) allows one primary only; promotion is restricted to synchronous standbys, so that no committed transaction is lost (RPO 0, NFR-1, `replica-architecture.md` §3); the synchronous quorum is checked by a monitor and an alert (`pg_stat_replication`); the WAN stability of etcd is validated before this design is accepted (AC-18); when automatic cross-region failover is replaced by an operator-approved one (`replica-architecture.md` §3.3, option 4), the runbook names the standby that may be promoted (R-06). |
| T-15 | Tampering | 4/5 | **A zombie executor** (paused, partitioned, wrongly declared dead) finishes its in-flight step after another node took the transfer over, and writes state or a part. | Every state-changing write carries the fence and affects nothing when it is stale (INV-3); part writes are idempotent per `(transfer, part_no)`; a node that cannot renew its lease stops (`replica-job-lifecycle.md` §6); the DBOS runtime fences the old executor at its next checkpoint, but not the step in flight (EXT, `replica-dbos-spike.md`); AC-7. |
| T-16 | DoS | 5 | **A poison job** crashes the executor on every attempt, over and over, on every node. | The reconciler keeps its own count of adoptions per transfer, because `ResumeWorkflows` resets DBOS's counter (`replica-dbos-spike.md`); beyond the cap the transfer is `FAILED(Internal)` and an alert is raised; `WithMaxRecoveryAttempts` is set and its `MAX_RECOVERY_ATTEMPTS_EXCEEDED` status is handled; panics in a step are recovered and classified; AC-19. |
| T-17 | Tampering | 2 | Someone with write access to the database (a compromised application role, an insider) changes a job: its destination, its policy, its state, a tenant's endpoint, a quota. | Separate roles for the API, the executors and the reconciler, each with the privileges it needs and no more; immutable columns after acceptance (source, destinations, policy) enforced by a trigger; endpoints changed only through the API; DDL only through the migration role; PostgreSQL reachable only from the nodes (SEC-15); the audit log is insert-only for every application role; accepted as R-02. |
| T-18 | Repudiation | 1/2 | A user denies a submission, a cancellation, a retry, a change of an endpoint or of a credential; the record is altered. | An append-only audit log with the principal, the tenant, the action, the resource, the result and the request ID (SEC-17), written in the same transaction as the change; insert-only privileges plus a trigger that refuses updates and deletes; the audit log is exported to a store outside the cluster. A hash chain and signed checkpoints, as in ligo, are future work (FW). |
| T-19 | Info disclosure | 8 | Logs, metrics, traces or the profiling files expose secrets, tenant data or tenant names. | Structured logging with the keys of `AGENTS.md` and a redacting filter; no object content and no credentials in logs or traces; per-tenant metrics with bounded label cardinality (`replica-acceptance-matrix.md` §1); CPU and memory profiling opt-in through the environment of the process (`REPLICA_CPU_PROFILE`, `REPLICA_MEM_PROFILE`) and off by default; core dumps disabled by the service unit. |
| T-20 | EoP / Tampering | 5 | **A malicious or compromised plugin.** A compiled-in driver runs with the process's memory: it can read every tenant's credentials in use and every object in flight. | v1 drivers are reviewed code in this repository only (PLG-1); drivers get credentials per attempt and keep no global state (PLG-5, PLG-6); the conformance suite and fuzz tests run on every driver; dependencies are scanned by `govulncheck`, dependency review and Dependabot on every change; accepted as R-07 until out-of-process plugins exist (OI-10, FW), which add a process and a trust boundary per driver. |
| T-21 | Tampering | 9 | **Supply chain.** A release artifact, a dependency or a build action is replaced or poisoned. | Releases are signed: the packaging key signs the checksums file, which covers every archive, package, SBOM and document, and the packages themselves (`.goreleaser.yaml`, `custom.mk`, `packaging/create-signing-key.sh`); the public key is published in `packaging/signing-key.asc` and the release workflow checks that it is the key that signs; the private key and its passphrase exist only as repository secrets and in an offline backup; an SBOM (CycloneDX) per package; GitHub Actions pinned by commit SHA, moved by Dependabot; `govulncheck` and the dependency review before every commit and in CI; the Setup Guide tells operators how to verify a release; the toolchain and the dependencies are updated regularly. |
| T-22 | EoP | 1/7 | A tenant administrator raises its own quotas, regions or limits beyond what the platform allows, or registers an endpoint outside its allowed ones. | Tenant overrides are bounded by the platform maximum (SEC quotas); tenant roles cannot change the platform's limits or `allow_private`; the platform-admin role is a separate role (SEC-4); changes of limits and endpoints are audited. |
| T-23 | Repudiation / Info disclosure | 7 | A platform administrator reads a tenant's data or jobs without leaving a trace. | The platform-admin role has no access to tenant rows; a break-glass action opens it, with a reason, for a bounded time, audited and alerted (SEC-4); the audit log is outside the platform administrators' write privileges. |
| T-24 | Tampering | 8 | The configuration or the environment file is changed to redirect the node: another state store, another identity provider, another secret backend, a relaxed policy. | Configuration and environment files owned by root, read-only for the service account, mode 0640; the service unit confines the process (`NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, no capabilities, a dedicated user); the hash of the configuration is logged and audited at startup; the configuration is validated at startup and the node fails fast (`replica-acceptance-matrix.md` §2). |
| T-25 | DoS | 1 | Abuse of the API: oversized or malformed bodies, expensive listings, floods. | Request size limits, strict JSON decoding, pagination with a maximum page, rate limits per tenant and principal (SEC-18); a listing only reads indexed columns scoped by tenant; timeouts on every handler. |
| T-26 | Spoofing | 1 | A client replays a submission, or uses another tenant's idempotency key to read its job. | Idempotency keys are scoped by tenant (`UNIQUE (tenant_id, idempotency_key)`): another tenant's key never matches; the same key with a different body answers `409`; the original job is returned only to the tenant that created it (FR-2, API-4); AC-13. |
| T-27 | Tampering / DoS | 2/3 | Clock skew or a clock jump makes a node think a lease expired (or did not): a live transfer is adopted twice, or a dead one never. | Leases and heartbeats compare timestamps taken from the database's clock (`now()` of the state store), not from the nodes'; the lease TTL has a safety margin over the heartbeat interval; nodes stop their transfers when they cannot renew (`replica-job-lifecycle.md` §6); NTP is a prerequisite and a node reports its offset; the fence makes a wrong adoption harmless (T-15). |
| T-28 | Info disclosure | 2/3 | Backups, WAL archives and replicas of the state store carry its content (job metadata, credential references, DBOS inputs and outputs) outside the cluster. | Backups and WAL archives encrypted, stored in a region other than the primary's, with access limited to the backup role; credentials are references, not values, except in the optional envelope-encrypted form (SEC-9); retention of the DBOS tables and of finished jobs is bounded (an acceptance scenario is to be defined with the retention policy). |
| T-29 | Info disclosure | 1/4 | An HTTP source or destination follows a redirect to another host and sends the tenant's `Authorization` header or credentials there. | The `http` driver follows no cross-host redirect and never forwards credentials across a redirect (SEC-13); the same for presigned requests. |
| T-30 | Spoofing / Tampering | 6 | A secret backend is impersonated or returns attacker-chosen credentials, so that tenants' data goes to the attacker. | TLS with certificate verification to secret backends, their addresses fixed in the platform configuration and not settable by tenants; the identity of the node to the backend is its workload identity (SEC-11); a credential is accepted only for the endpoint that references it. |

## 4. Accepted residual risks

| ID | Risk |
| :--- | :--- |
| R-01 | `replica` replicates what it is given: an object that was already corrupt or malicious at the source, before its first read, is copied faithfully. The recorded digest proves that the copies equal the source as first read, not that the source is right (T-08). Scanning content is out of scope. |
| R-02 | A compromise of the application's database role can alter jobs and state across tenants within the privileges of that role; the audit log, its insert-only privilege and the immutable columns limit the damage and keep a trace (T-17). |
| R-03 | A tenant's storage credential is as powerful as the tenant made it: `replica` can limit the operations it performs with it, not what the credential allows (T-05). |
| R-04 | A zombie executor can finish one in-flight part after another node took over. The part write is idempotent, so the objects are not affected, but the bandwidth is spent twice (T-15). |
| R-05 | A region partitioned from the other two cannot accept jobs, by design (T-13). Jobs already accepted continue on the majority side. |
| R-06 | When cross-region failover of the state store is operator-approved, the recovery time of a region loss is as long as the operator's reaction, and promoting the wrong standby loses transactions that the synchronous one holds (T-14). The runbook names the standby; the monitor shows which one is synchronous. |
| R-07 | In v1 a plugin shares the process with the core and with every tenant's credentials in use; a malicious driver is a full compromise. Only reviewed drivers in this repository are linked (T-20). |
| R-08 | The platform's security rests on the identity provider's and the tenants' assignment of roles: `replica` cannot tell that a tenant admin registered an endpoint that points to a system the tenant should not read, as long as the endpoint is within the platform's allowed ones. |
| R-09 | Verified releases rest on the packaging key: whoever holds the private key and its passphrase can sign. Its custody (the repository's secrets and one offline backup) is the maintainer's responsibility (T-21). |

## 5. Verification

Every threat that names an acceptance scenario is checked there (`replica-acceptance-matrix.md` §4); the others are checked by the tests of their mitigations, which are written before the implementation (`AGENTS.md`, rule 4). Open points to settle with the specification of the affected component:

- the retention policy of the DBOS tables, jobs and audit entries (T-28), and its acceptance scenario;
- the quota catalog (T-11, T-22), which `replica-tenancy.md` §4 lists but does not number;
- the exact roles and privileges of the database (T-03, T-17), to be written with the migrations;
- the hash chain of the audit log (T-18), if the review wants it in v1.
